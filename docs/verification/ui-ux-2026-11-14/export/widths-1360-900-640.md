# 1360 / 900 / 640 × 900 的导入导出抽屉证据（T12）

证据类型：**headless 布局级**（不是原生像素截图，见 `README.md`）。三个宽度各自开一个 900 高的 GPUI 测试窗口，窗口里放真实的 `ExchangePane`，并按外壳（`chrome.rs` 的 `exchange_layer`）同一套几何套一个抽屉框：宽 `min(520, 视口-60)`、内部 `overflow_y_scroll`。由 `exchange_states_hold_at_1360 / _900 / _640` 在浅色/深色 × 紧凑/标准 四种组合下逐格断言。

## 几何前提

- 抽屉宽度公式来自 `src-tauri/src/app/shell/chrome.rs` 的 `.w(px(520.0_f32.min(self.model.viewport_width as f32 - 60.)))`；外壳的最小窗口是 640×420（`src-tauri/src/app/mod.rs` 的 `window_min_size`），所以真实使用中抽屉恒为 **520**：640 视口下 `min(520, 580) = 520`，900 与 1360 也是 520。
- 因此三档宽度之间**面板宽度相同**，差异只在页边距：`Metrics::for_viewport(视口宽)` 在视口 < 760 时把 `page_pad` 钳到紧凑档（16），900/1360 下按密度取 20（标准）/16（紧凑）。
- 用例里的抽屉框宽度与上面公式逐格比对（`assert_inside_drawer`），不是写死 520 的假设。

## 窄宽的具体处理

- 面板的分区间距与页边距都取 `metrics`（`Metrics::for_viewport`），不在渲染里写死像素。
- 来源、导出、导入、任务四个容器都有 `min_w(px(0.)) + max_w_full()`：面板再窄时内容按容器宽收窄，而不是把面板撑宽。
- 导入预览的三按钮页脚与任务区的两个工具按钮都加了 `.flex_wrap()`：真的挤不下时换行，而不是把按钮推出面板（抽屉固定 520 时不会触发，属于窄窗口/更长本地化文案的兜底）。
- 被挡住的行动作本身是整行块（图标 + 三行文字），文字块有 `flex_1 + min_w(0)`，长原因按行宽换行。
