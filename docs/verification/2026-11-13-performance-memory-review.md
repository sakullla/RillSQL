# 性能与内存复查（v0.2.24）

日期：2026-11-13。基线为 v0.2.23 / `98b6692`；本轮直接审查和实现，未使用 workflow 或委派审查。

## 审查与改动

- 查询生命周期：沿 GPUI 的启动、快照传递、终态接收及取消路径检查。原有 `release_run` 没有被当前查询视图调用，完成后的运行会保留后端结果。现在接收端处理终态并关闭后释放；视图提前消失时继续收完已发起的执行并清理，不重放写语句。
- 快照内存：将无界通道改为容量 1 的通道，让慢 UI 对读取产生背压。只限制待处理快照，不改变用户设置的结果行上限；进行中的驱动结果和正在发送的快照仍需要内存。
- 网格所有权：来源行、排序/筛选视图和暂存保留行共享 `Arc<GridRow>`；修改原值使用写时复制。复核了行定位、追加页、编辑、新增、提交、导出和缓存消费者；稳定行 ID、NULL、预览及暂存语义保持不变。
- 网格 CPU：排序与筛选借用单元格字符串；追加页通过集合去重；完整值缓存按行 ID 和列名索引，清理时不再逐缓存扫描行列表。空缓存且没有查看目标时跳过清理扫描。
- 复查了相邻查询执行、任务登记、目录与文件导出路径。本轮改动集中于已证实的结果驻留、队列积压及网格重复数据；不对其它路径或所有负载作统一收益承诺。

- `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --locked`：通过；已有警告仍在，改动路径未产生新警告。
- `node .github/scripts/release.mjs check v0.2.24`、`node --test .github/scripts/release.test.mjs`：版本检查及 12 项发布测试通过。

- 新回归用真实 SQLite 连续执行 6 次包含写入和 1,000 行查询的批次，交替正常消费与关闭接收端。每次结束后后端运行登记归零，6 条写语句恰好执行一次；还检查快照顺序和通道容量。
- 新回归检查排序/筛选/保留行共享、旧快照与写回隔离，以及完整值缓存的列隔离、Ready(NULL)、隐藏来源行和删除清理。

## 合成内存与耗时证据

环境：macOS 27.0 ARM64，rustc 1.98.1，未优化的 test profile。10,000 行 × 8 列，每格 128 字节。比较旧的行深拷贝操作与新的完整 `recompute`，每轮核对内容一致及共享指针身份：

| 轮次 | 旧行深拷贝 | 新视图重建 |
| --- | ---: | ---: |
| 1 | 2,982 µs | 418 µs |
| 2 | 2,456 µs | 398 µs |
| 3 | 2,458 µs | 399 µs |

共享视图避免额外复制 10,240,000 字节（约 9.77 MiB）的单元格文本，不含容器、ID 和分配器开销。原始数据仍驻留；Arc 和视图指针也有开销。这不是整机 RSS 或真实数据库吞吐测量，旧列仅计深拷贝，不能当作旧版本完整重建耗时。

复现：`cargo test --manifest-path src-tauri/Cargo.toml --locked --lib benchmark_grid_shared_rows -- --ignored --nocapture`。
